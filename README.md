# 🛒 sourcing-agent — 跨境电商选品 + 上架 Agent

[![CI](https://github.com/xianteng-zhang/sourcing-agent/actions/workflows/ci.yml/badge.svg)](https://github.com/xianteng-zhang/sourcing-agent/actions/workflows/ci.yml)
![Python](https://img.shields.io/badge/python-3.12-blue)

基于 LangGraph + 大语言模型的跨境电商选品 + 上架 Agent。从商品评论中自动挖掘**卖点、痛点、关键词和竞品差异**,并生成合规的多语言 Listing 上架文案。

## 功能一览

| 功能 | 输入 | 输出 |
|------|------|------|
| 🤖 **选品 Agent** | 竞品评论 CSV + 卖家产品规格 | LLM 自主决定调用 6 个工具中的哪些、什么顺序(实测支持并行调用);两类确定性闸门把关**违禁词**与**编造参数**;对外发布属外部副作用,**无人工批准一律拒绝**,产出可上架 Listing |
| 📊 **评论挖掘** | 单个商品的评论 CSV | 结构化选品报告(官方星级分布 / 口碑 / 卖点 / 痛点 / 关键词 / 竞品线索 / 选品结论) |
| ⚔️ **竞品对比** | 多个竞品的评论 CSV | 对比报告(概览表 / 卖点痛点横向对比 / 差异化机会 / 选品建议) |
| 🌐 **类目占位 · AI 可见度** | 我的品牌 + 一批类目问题 + 竞品名单 | 买家问 AI「这个类目该买哪个」时 AI 推的是谁:**推荐位被谁占了 / 头部位次稳不稳 / 有没有你没想到的对手**。分母只算有效样本,附每条指标的原文溯源 |
| 📈 **趋势分析** | 关键词 | Google 搜索热度走势 + 上升/下降判断 |
| 📚 **历史记录** | — | 每次分析自动保存,可回看 / 删除 |

## 如何获取评论 CSV

**方法 1:自研评论抓取扩展(推荐,一键导出,支持亚马逊 + 速卖通)**

1. 在界面左侧边栏**下载扩展 zip** 并解压
2. Edge 打开 `edge://extensions/` → 开「开发人员模式」→「加载解压缩的扩展」→ 选解压出的文件夹
3. 亚马逊:打开评论页,往下滚动加载评论;速卖通:打开商品页即可
4. 点扩展图标 →「抓取当前页评论 → CSV」,自动下载

**方法 2:Instant Data Scraper 插件(通用备选)**

1. 浏览器(Edge/Chrome)安装 **Instant Data Scraper** 插件
2. 打开亚马逊商品的**评论页**(点「See all reviews / 查看所有评论」)
3. 往下滚动几屏,让评论加载出来
4. 点插件图标,弹出的预览**默认选中的往往不是评论**——点顶部的「**Try another table**」切换,直到预览变成「一条评论一行」
5. 确认后点「Download CSV」导出

**方法 3:手动复制到 Excel(简单可靠)**

1. 打开商品评论页,复制 20~30 条评论
2. Excel 里做两列:`rating`(评分 1~5)、`review`(评论内容)
3. 「文件 → 另存为」选 **CSV UTF-8**

**方法 4:先用示例数据体验**

- 不传文件,界面上勾选「使用示例数据」即可先看效果(示例在 `data/sample_reviews.csv`)

> 💡 工具**不挑平台**:亚马逊、速卖通、Shopee、TikTok Shop……任何平台导出的评论 CSV 都能分析。

## CSV 格式(智能识别)

**列名无所谓**,工具会自动识别。支持:

- 标准列名:`review` / `comment` / `内容` / `评论`(正文)、`rating` / `score` / `评分`(评分)
- 插件导出的网页类名:`a-size-base`、`cr-original-review-content`、`a-icon-alt` 等
- 识别逻辑:先按列名匹配 → 匹配不上就按**内容特征**推断(哪列文本最长 = 评论、哪列值像评分 = 评分)

没有评分列也能跑,只是少了「平均分 / 好评占比」统计。

> 自研扩展抓取的 CSV 第一行会带 `# 平均分=… 总评数=… 5星=…` 这类**官方星级分布元数据**,工具会自动识别并在报告里优先采信(基于全部评论,比样本更权威)。

## 工作原理

**评论挖掘**是典型的 Map-Reduce:

1. 读 CSV(自动探测 UTF-8 / GBK 编码)
2. 把评论分成小批(默认每批 25 条),每批让 LLM 提取「卖点 / 痛点 / 购买动机 / 竞品提及」
3. 汇总所有批次结果,再让 LLM 生成最终 Markdown 报告

**竞品对比**:

1. 用 `ThreadPoolExecutor` **多线程并行**分析每个竞品(LLM 调用是 IO 密集,并行提速)
2. 全部完成后,由一次汇总调用生成差异化对比报告

**选品 Agent**(LangGraph ReAct):

1. LLM 绑定 **5 个工具**:竞品评论挖掘 / 关键词挖掘 / Listing 生成 / 多语言翻译 / 合规审查
2. LLM **自主规划**调用哪些工具、什么顺序,并**流式执行**,每步实时展示。
   实测一次真实运行:第 1 轮**并行**调用 `analyze_reviews` + `extract_keywords`
   (5 个工具里只有这两个彼此无依赖),之后串行 `generate_listing` → `compliance_check`。
3. **两类确定性闸门**先于模型判定,命中即判不合格、**不调用模型**、LLM 无权推翻:
   - `compliance.py`:违禁词 / 促销语 / 绝对化用语 / 未授权认证
   - `spec_anchor.py`:**参数锚定** —— Listing 里的数值型参数必须能在卖家填写的规格里
     找到,查不到即为候选编造(规格写 320 克、文案写 320g 不算违规)
   两类都通过后,才交给 LLM 细查参数单位 / 标题格式 / 关键词堆砌。
   `generate_listing` 以其构成「生成 → 拦截 → 重写」闭环,最多 3 轮。
4. **卖家规格通过闭包注入工具,不经过模型中转** —— 否则模型漏抄或截断规格时不会报错,
   只会安静地产出一份全是【待填写】的 Listing。

## 工程底座:持久化 / 治理 / 可观测

这三件事都不在「模型能不能干」的范围内,而是「干到一半出事了怎么办」——
也正是 Demo 和能用的东西之间的差别。

### 批量任务跑在 SQL 持久化队列上(`jobs.py`)

内存线程池里「谁在跑」只活在进程内。进程一挂(关窗口、OOM、断电),在跑的任务
既没结果、也没人知道它们跑过,重启只能整批重来 —— LLM token 白烧一遍。

改成 claim / lease / reaper 之后,崩溃的后果变成三档:

| 崩溃时的状态 | 结果 |
|---|---|
| 已完成 | 直接读结果,**不重跑** |
| 租约过期 | reaper 捞回 pending,换个 worker 重跑 |
| 超出重试上限 | 落到 `dead`,不再无限重试 |

**租约是这里的关键**:进程死了没法主动归还任务,所以「占用」必须带过期时间,
由**别人**来判断它是否已经死了。并发正确性靠 `BEGIN IMMEDIATE` + 条件 UPDATE 保证。

竞品对比已经从 `ThreadPoolExecutor` 迁到这条队列上:同一个 run_id 重复调用是幂等的,
所以用户关掉窗口再打开只会补跑没做完的那几个竞品。

#### 失败之后要**等一会儿**再重试(`next_attempt_at`)

「退回 pending」原先等于「马上被重领」。**但那不是重试,是撞墙** —— 尤其是 429,
同一堵墙会连撞三次,三次额度全烧掉,任务落 dead。接第二个厂商(真实跑 Kimi)时
就是这么被打的。

所以失败后不是立刻可领,而是排一个 `next_attempt_at`:

```
第 1 次失败 → 等 2s
第 2 次失败 → 等 4s
第 3 次失败 → 落 dead
```

**为什么要抖动**:多个 worker 同时被限流,如果都精确等 `2^n` 秒,它们会**同时醒来
再一起撞上去**(thundering herd)。所以用「等比例抖动」—— 保证至少等一半,
另一半随机,把重试时间摊开。上限 60s。

**一个容易漏的地方**:有了退避,「领不到任务」就有了两种含义 —— *活干完了*,
或者*剩下的都在退避中*。分不清的话 worker 会提前收工,把还在退避的任务丢在那儿
没人管。所以 `claim()` 返回 None 之后要问一句 `next_attempt_in()`,返回 None
才表示真的没活了。

#### 可重试的失败必须**抛出去**,不能吞成数据

这是同一轮里挖出来的更根本的问题。采集层用 `safe_ask` 把任何异常收敛成一条
**失败的 Answer**(这是对的,失败要以数据形式进库)。但队列据此认为「这个任务成功了」:

```
真实跑 Kimi 时的队列状态:  done: 8   dead: 0     ← 看着一切正常
实际发生的事:              3 次 429 被吞成了 Answer
后果:                      退避和重试机制一次都没被触发过
```

修法:`run_one` 对**可重试**的失败(超时 / 限流 / 未知)`raise`,交给队列;
不可重试的(解析失败 / 鉴权 / 被拦)才落成数据 —— 那些重试也没用。
重试用尽落 dead 之后,采集层再把它**补回一条失败记录**(分类从错误串里还原),
这样它既不进分子也不进分母,但看得见。

### 动作分三级,外部副作用默认拒绝(`actions.py`)

Agent 手里的工具不是平等的:

| 分级 | 动作 | 执行条件 |
|---|---|---|
| 只读 | 评论挖掘 / 关键词 / 合规检查 | 直接执行 |
| 可补编辑 | 生成 Listing / 翻译 | 直接执行,结果标记为草稿、记审计 |
| **外部副作用** | **发布 Listing** | **没有人工批准就绝不执行** |

关键在最后一行:**默认拒绝,而不是默认放行**。模型说「用户已经同意了」不算数,
批准只能由人通过界面写进库;而且批准**绑定到具体内容**(payload 哈希),
所以「批准了这一版文案」不能拿去发改过的另一版,也不能拿别的动作的批准来顶。

每次尝试(放行或被拦)都记进审计表,可以事后查「谁在什么时候想干什么、被谁拦下的」。

### 运行事件可回放(`events.py`)

一次运行会产出几十个事件。只存在这次渲染里的话,刷新页面、切走一会儿再回来,
前面发生过什么就没了,只剩最终结果 —— 想查「它到底调了哪几个工具、顺序对不对」
只能重跑。

现在每个事件带一个**单调递增的 seq** 落库。客户端记住自己收到的最后一个 seq,
断线后带上它重新连,服务端只回补**比它大**的那些:断线期间的不丢,已经收到的
不重复。两个容易写错的地方都有测试钉住 —— 回放必须是 `> last_event_id`(写成
`>=` 就会把最后一条重复渲染),以及 seq 在同一 run 内必须连续唯一。

**历史记录里存了一个 `run_id` 指回这里**,所以「历史记录」里每一条报告都能展开
回放**当时那次运行**:调了哪几个工具、什么顺序、每步的动作分级。存的是引用而不是
把事件复制一份 —— 复制会造成两份数据,还可能不一致。

## 测试

```bash
pip install -r requirements-dev.txt
pytest -q
```

178 个用例分七个文件。除了各钉一类**静默失效**(不报错、照常出结果、只是悄悄错了)
之外,还有几个文件专门钉「出事之后会怎样」。

**`test_review_miner.py`(14 例):脏 CSV 的列识别与评分解析。**
这是整个工具唯一直接面对不可控外部数据的地方,上游插件换一版导出格式,识别逻辑就会失效。

- **纯数字评分列**:`_parse_rating` 原先只认 `5.0 out of 5 stars` / `4.0 颗星` 两种文本,
  而 `_detect_rating_column` 却把纯数字列也判定为评分列——于是评分列被「识别出来」却「解析成空」。
  自带示例数据正好走这条路径,概览卡片的平均分和好评占比全丢。
- **lightbox 干扰列**:只按「平均文本长度」挑评论列,会选中弹窗那种「行数少但单条极长」的列;
  `_detect_review_column` 的排序键必须是「非空行数优先、平均长度次之」。

**`test_compliance.py`(35 例):两类确定性闸门 + 重写闭环。**
闸门失效是「漏拦」(最危险),闭环失效是「空转」(最烧钱),两类都钉住。

- **误报边界**:`100% 棉` 是合法参数,`100% 有效` 才是违规;裸写 `CE` 会误命中 `CERTIFIED`,
  所以认证类规则用 ASCII 字母边界而非 `\b` —— 中文是 Unicode 词字符,`\b` 在「FDA认证」里根本不成立。
- **自检表引用违禁词**(真机联调踩到):模型会在 Listing 后附一张「合规自检对照」表,
  里面**引用**「最好 / 包邮 / 终身保修」来说明「未出现」。逐词扫描会把这些**引用**当成真实违规,
  **重写闭环于是永远无法收敛** —— 每轮白烧 3 倍 token,还始终报不合格。
  修复后同一用例从 **3 轮 15.6s 不通过** 降到 **1 轮 4.2s 通过**。
- **参数锚定的误报边界**:规格写「320 克」而文案写「320g」必须放行(所以判定比的是
  **数值**而不是「数值+单位」);`5 min` 不能被当成 `5m`、`8GB` 不能被当成 `8g`
  (单字母单位后面加了 ASCII 字母边界);全是【待填写】的文案是正确的,不能拦。
- **数值比对必须归一化**:规格写 `320`、文案写 `320.0g` 是同一件事。

**另四个文件专门钉「出事之后会怎样」:**

- **`test_jobs.py`(29 例)**:并发领取不重复发放、租约过期能回收、超限落 dead,
  以及最要紧的那条 —— **跑到一半崩溃,重启后已完成的不重跑、只补没做完的**。
  还包含竞品对比接上队列后的续跑行为(重跑不再喂一遍 LLM),以及三条回归:
  **进度回调必炸时任务状态不许被改坏**、**失败后不能立刻被重领(退避)**、
  **老库要能原地补上 `next_attempt_at` 列**。
- **`test_actions.py`(25 例)**:外部副作用**没有批准就不能执行**(且断言被拦时
  底层函数一次都没被调用过);批准绑定动作与内容 —— 改一个字、换个动作、过期了都不算。
- **`test_events.py`(12 例)**:回放严格取 `seq > last_event_id`、并发写不撞 seq、
  跳号能被自检发现。
- **`test_engines.py`(56 例)**:多引擎答案采集 —— 四条**口径**
  (①失败不进分母 ②失败**不能**被算成「没提到品牌」③提到 ≠ 被推荐
  ④同一问题样本自相矛盾时指标不可当结论)、**类目占位**
  (位次→品牌映射、竞品表之外的推荐项、头部位次易手、同一条答案里出现两次只算一次)、
  配置发现与 `temperature` 的坑,以及三条工程不变量:重跑同一个 `run_id`
  **一次引擎都不调**(断言调用计数为 0)、队列里死掉的任务**必须补成一条失败记录**、
  **可重试的失败要真的被重试**(而不是被吞成数据)。
  全部走 `engines/recordings/` 的录制回放,**不联网、不花钱**。

> **`test_storage.py`(7 例)** 单独钉历史库的 `run_id` 迁移:老库要能原地加上新列。

> **三个文件里都有一条「全新库」回归用例**:读方法必须自己建表,不能假设别人先写过。
> 这条是 app 启动即崩(`no such table: approvals`)之后补的 —— 之前的用例全都先写过一次,
> 所以谁都没暴露这个问题。

### 跑界面挖出的队列 bug

接了「AI 可见度」这个新页之后,用 Streamlit 官方的 `AppTest` 把整个脚本**端到端**
跑了一遍(不只测函数,而是真的点按钮),结果进度条报出 **116%**。追下去是队列里
一个潜伏很久的正确性问题:

```
progress() 原先写在 try 里面,而 except 分支做的事是 queue.fail()。
回调只要抛一次异常:
  · 一个刚刚 complete() 过的任务会被 fail() 翻回 pending —— 白跑一遍
  · done_count 在 except 里被重复 +1 —— 进度冲过总数
```

修法:**任务的 `try/except` 只管任务本身**;进度回调挪到状态落库之后、`try` 之外,
并且单独 `try` 住 —— 进度是展示,它坏掉不该影响任何一个任务的最终状态。

同一类问题还牵出两处:竞品对比页和 AI 可见度页都在**工作线程**里调 `st.progress`,
而工作线程没有 Streamlit 的脚本上下文,会抛 `NoSessionContext`。

> **教训**:纯函数测试全绿,不代表把界面点一遍也能跑通。**跨线程 + 回调 +
> 状态机**这三样凑在一起时,只有真的点一次才发现得了。

### 纯 CSS 的 bug,`AppTest` 抓不到

为了去掉 Streamlit 的开发态痕迹,我一开始把 `[data-testid="stToolbar"]`
**整个** `display: none` 了。结果:**侧边栏一收起就再也打不开**。

原因很隐蔽 —— 「展开侧边栏」那个按钮(`stExpandSidebarButton`)就住在 toolbar 里面:

```
stExpandSidebarButton   inToolbar: true   visible: false   w: 0  h: 0   ← 被连带藏了
```

修法是只藏 Deploy 和右上角菜单,把 toolbar 本身留着:

```css
#MainMenu,
[data-testid="stMainMenu"],
[data-testid="stAppDeployButton"],
[data-testid="stDecoration"],
[data-testid="stStatusWidget"],
footer { display: none !important; }
```

> **教训**:`AppTest` 只执行 Python 逻辑,**不碰布局**。所以
> **CSS 类的 bug 它一个都抓不到** —— 只能靠真浏览器点。
> 定位这种问题最快的办法是查 DOM 而不是看代码:一眼就能看到
> 「那个按钮确实存在,只是 `visible: false`」。

### `engines/` — 多引擎答案采集与类目占位

把「同一批类目问题拿去问 N 个 AI」做成可重试、可归因、可复现的事。分层如下:

```
engines/base.py            # 契约:Answer / 6 类失败分类 / Engine 协议 / safe_ask
engines/store.py           # 原文留存:每个采样点一行,指标靠 answer_id 回到原文
engines/replay.py          # 录制回放:测试与复核不碰网络(recordings/*.jsonl)
engines/openai_compat.py   # 真实引擎:一个类覆盖所有 OpenAI 兼容接口
engines/collect.py         # 编排:多引擎 × 多问题 × N 采样,跑在已有租约队列上
engines/metrics.py         # 口径:提及率 / 进榜率 / 覆盖率 / 稳定性 / 可比性告警
engines/occupancy.py       # 占位:这个类目的推荐位被谁占了(选品要的是这个)
```

**`metrics.py` 和 `occupancy.py` 回答的是两个不同的问题:**

| | 问的是 | 给谁看 |
|---|---|---|
| `metrics.py` | **我这个品牌**在 AI 答案里表现如何 | 上架之后做效果追踪 |
| `occupancy.py` | **这个类目的推荐位**被谁占了 | **选品阶段决定进不进** |

占位分析里最有价值的一条是 **AI 会告诉你你不知道的对手**:

> 你只能把已经知道的竞品填进名单,但 AI 推荐里冒出来的那些没在名单上的品牌,
> 会被单独列出来 —— 那些才是你漏看的。

第二条是 **头部位次稳不稳**:如果 #1 在不同采样之间易手,说明这个类目的 AI
入口没有锁死,那才有缝;如果永远是同一个大牌,别进。

不带参数直接跑,会用录制样本走完整流程(不联网、不花钱):

```bash
python -m engines
```

输出里会看到四件事:**失败被剔除出分母**、**这个类目的推荐位被谁占了**、
**第二轮一次引擎都没调**,以及**任意一个指标能拉回产生它的原文**。

演示数据本身就是中文的,构造了一个「有缝」的类目(便携咖啡机):
两个问题的第 1 位都在样本间易手,并且冒出两个没列进竞品名单的对手
(`AeroPress Go` / `Outin Nano`)。

## 成本提示

- 评论分批喂给 LLM,数量越多 token 消耗越大。默认**最多分析 300 条**(超出均匀抽样)。
- 想省钱:`.env` 里把模型改成 `deepseek-flash`(更快更便宜)。

### 当前该用哪个模型名

以[官方定价页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)为准,现在只有两个:

| | `deepseek-flash` | `deepseek-v4-pro` |
|---|---|---|
| 模型版本 | DeepSeek-V4.1-Flash | DeepSeek-V4-Pro |
| 输入·未命中(空闲) | 1 元/百万 | 4.5 元/百万 |
| 输出(空闲) | 4 元/百万 | 13.5 元/百万 |
| **并发限制** | **2500** | 500 |
| 图像理解 | ✅ | ❌ |

本项目默认 `deepseek-flash`。**多引擎采集尤其该用它** —— 采样数随
「引擎 × 问题 × 采样次数」线性涨,而并发限制直接决定队列能开多少 worker。

两点容易被忽略:

- **老名字 `deepseek-chat` 已不在官方表里**(实测仍可调用、由 V4.1-Flash 提供服务)。
  遗留别名哪天消失是不通知的,所以直接用当前名。
- **空闲时段价格是高峰的一半。** 高峰 = 工作日 9:00-12:00 与 14:00-18:00;
  其余(含晚上、周末、法定节假日)都是空闲 —— 批量采集放到晚上跑能省一半。

## 常见坑

- **趋势分析需要能访问 Google**:`pytrends` 访问 Google Trends,国内需要系统级代理;代理关了趋势会查不到,但评论挖掘和历史记录不受影响。
- **中文关键词趋势**:Google 上中文搜索量偏低,趋势图可能很平,英文关键词效果更好。
- **pip 安装慢**:清华镜像对部分包返回 403,可用阿里云镜像:`pip install -i https://mirrors.aliyun.com/pypi/simple/`。
- **改了 `config.toml` 的主题不生效?先看服务端 stderr。** 这个坑很阴:
  `theme.baseFontSize` 要的是**整数**(`15`),写成 `"15px"` 会让 protobuf 赋值抛
  `TypeError`,而 Streamlit 的处理方式是**整个 `[theme]` 块都不要了**,静默回落到
  默认配色(那个 `#FF4B4B` 的红按钮)。**页面上没有任何提示**,只在服务端 stderr
  留一条 traceback。所以主题改了没反应,第一步是去看服务端日志,不是去改 CSS。

## 界面主题

配色在 `.streamlit/config.toml` 里,调色板 = slate 中性色阶 + 单一靛蓝强调色。

**一条原则:能写在配置里的,就不要写进 CSS。** 配置项是版本稳定的;靠 CSS 选择器
去猜 Streamlit 的 DOM 结构,一升级就会碎。所以颜色、圆角、字号层级、状态色
(成功 / 警告 / 危险 / 信息)全部声明在配置里:

```toml
[theme]
primaryColor             = "#4F46E5"   # 靛蓝
backgroundColor          = "#FFFFFF"
secondaryBackgroundColor = "#F8FAFC"   # slate-50
borderColor              = "#E2E8F0"
textColor                = "#0F172A"
baseRadius               = "0.65rem"   # 一个基准值派生到所有控件
baseFontSize             = 15          # ⚠ 必须是整数
headingFontSizes         = ["1.7rem", "1.3rem", ...]
greenColor / yellowColor / redColor / grayColor / ...
```

留给 CSS(`app.py` 里的 `_SKIN`)的只有**配置表达不了的三件事**:

1. **藏掉开发态痕迹** —— `Deploy` / 工具栏 / 页脚。留着它,界面就在替你喊「我是 demo」。
   ⚠️ 但**不能整个藏 `stToolbar`**:展开侧边栏的按钮就在里面,藏了整个就再也展不开。
2. **收窄内容宽度** —— `layout="wide"` 会让表单拉满整个屏幕,眼睛要横扫。
3. **卡片的边框与阴影** —— 配置项管不到 `box-shadow`。
